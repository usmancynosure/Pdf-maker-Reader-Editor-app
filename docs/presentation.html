What is Prisma Scan? (in plain words)

Think of it as "CamScanner meets a PDF editor." You point your camera at a paper document; the app finds the paper's edges, straightens it, and makes it look clean — like a real scan. Then you can save it as a PDF and do everything a PDF app does.

Scan

Camera with automatic edge-detection and multi-page capture.

Create

Enhance with filters and export a clean, shareable PDF.

Sign

Read, reorganize, watermark and add your signature.

The problem it solves: people constantly need to turn paper (receipts, IDs, contracts, forms) into tidy digital PDFs — and then tweak or sign them — without a desktop scanner. Prisma Scan does it all on the phone.

How it's built — architecture

The code is organized feature-first: each feature (home, scanner, reader…) is its own folder, and inside it the code is split into 4 layers. This keeps things easy to find and test.

Data flows top → bottom · a tap on a screen calls a provider, which calls a service, which returns a model

Why this design? New features slot in as a new folder without touching others. The UI never talks to native code directly — it always goes through a provider and a service, so any piece can be swapped or tested in isolation (e.g. the mock in-app-purchase service).

Under the hood — the Scan → PDF pipeline

This is the app's core magic. The slow image work runs on a background isolate (a separate thread) so the screen never freezes.

ACaptureNative scanner returns image files
BEditPick filter + rotation per page
CProcessRotate + filter pixels (isolate)
DBuild PDFAssemble A4 pages
ESave + listWrite file → documentsProvider

Native scanning

Uses the phone's own scanner — VisionKit on iOS and ML Kit on Android — for the best edge-detection with the least code.

Editing existing PDFs

Merge, split, reorder, watermark and sign are done with the Syncfusion PDF library by copying page content into a new document.

07

Interview questions & answers

Likely questions about this project, with short answers you can say out loud.

QWhy did you choose Flutter for this app?Basics

One codebase ships to both iOS and Android with near-native performance, a rich widget set for the custom glassmorphism UI, and easy access to native features (camera, files) through plugins. It cut development time roughly in half versus building two native apps.

QWhy Riverpod instead of setState or Provider?State

The document list, settings and bookmarks are shared across many screens. Riverpod gives compile-safe, globally-accessible state without BuildContext, easy dependency injection (services are providers, so I can swap a real service for a mock in tests), and fine-grained rebuilds with .select(). setState only fits local, single-widget state.

QExplain your project's folder structure.Architecture

Feature-first: each feature folder (home, scanner, reader, editor, files, settings…) contains presentation (UI), application (Riverpod providers), data (services/repositories) and domain (plain models). Shared building blocks live in core/ (theme, router) and shared/ (reusable widgets). Features stay independent and testable.

QThe image processing is heavy — how do you keep the UI smooth?Performance

The pixel work (rotate + filter + build the PDF) runs on a background isolate using Flutter's compute(). Dart is single-threaded per isolate, so doing this off the UI isolate keeps the main thread at 60fps. A loading overlay shows progress while it runs.

QHow do you scan documents — did you build edge-detection yourself?Native

No — I use the platform's own document scanner (Apple VisionKit on iOS, Google ML Kit on Android) via a plugin. It already does high-quality edge-detection and perspective correction. Reusing it means better results, less code, and it stays maintained by the OS vendors.

QHow do you edit an existing PDF (merge, split, reorder)?PDF

With the Syncfusion PDF library. I load the source PDF, then build a new document by importing each page as a template into the order I want; deleted pages are simply skipped, rotation is applied per page, and merge just pulls pages from a second file. Watermark and signature are drawn onto a page's graphics before saving.

QThe whole app is a light "holographic" theme. How did you handle dark-mode devices?Theming

The design is a deliberate single visual world, so I force the light theme app-wide (ThemeMode.light). This avoids the classic bug where a forced-light bottom sheet inherits dark-theme text and becomes invisible — a real issue I caught and fixed by locking the theme.

QHow is the app monetized, and is the payment code done?Business

Freemium with a Pro paywall (weekly/yearly/lifetime). Payments sit behind a PurchaseService interface with a mock implementation that unlocks locally so the flow is fully testable. Going live is just implementing that interface with RevenueCat — no UI changes needed.

QHow do you store documents and settings?Storage

Generated PDFs are written to the app's documents directory via path_provider; each Document model keeps the file path. Small key-value settings (app lock, export quality, Pro status) use shared_preferences, loaded once at startup and injected through a provider override.

QWhat was the hardest bug you fixed?Debugging

The raised center scan button was being clipped: it lived inside the nav bar's ClipRRect, so the part poking above got cut off. I restructured the nav into a Stack with clipBehavior: Clip.none and overlaid the button on top. Also the dark-mode invisible-sheet bug mentioned above.

QHow would you test this app?Quality

Unit-test the services and models (PDF export, date formatting, document logic) with mocked providers; widget-test key screens; and use integration tests for the scan→save→read flow. Because services are injected via Riverpod, swapping real ones for fakes is trivial.

QIf you had more time, what would you improve first?Vision

OCR (searchable text + export to Word), real cloud sync, and folders. Then password-protected PDFs and PDF compression — see the roadmap below.
